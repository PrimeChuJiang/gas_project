## 第 1 步：邮局事件流（关账）

### 概念课（UE GameplayCue 是什么）

- 表现层（视觉/音频）与逻辑完全解耦；GE 配 tag = "表现地址"；
- `UGameplayCueManager` = 邮局：tag → 处理者注册表，广播分发；
- 四事件（`EGameplayCueEvent`）：OnActive / WhileActive / Executed / Removed；
  两类通知者：Static（一次性）vs Actor（持续，被 spawn 进 world）；
- **信号只出不进**：逻辑对表现零引用。

### 落地（用户写，多轮审查）

- `GASEnums.GameplayCueEvent` 四枚举（对齐 UE 原版名）；
- `GASGameplayCueManager`（Autoload，`gameplay_abilities_system.gd._enter_tree`
  `add_autoload_singleton` 注册，project.godot 落定）：
  - `HandlerList` **内嵌薄类**（RefCounted）：Array[Callable] 注册表 + register
    （去重 warn）/ unregister（倒序遍历删除）/ broadcast（快照 `duplicate()`）；
  - `_handlers: Dictionary[FGameplayTag, HandlerList]`——typed dict + 用户类值，
    这是嵌套泛型被拒后的正解（`Dictionary[FGameplayTag, Array[Callable]]` 非法）；
  - 决策：重复注册 = 忽略 + warn；查无 handler = **静默**（表现空白合法，
    后续地城回归十几次眩晕广播零报错实证）；
- ASC 三处钩子（`ability_system_component.gd`）：
  - INSTANT apply 后 → EXECUTED（:53）
  - DURATION/INFINITE 挂账后 → ON_ACTIVE（:113）
  - `remove_active_effect` → ON_REMOVED（:134）——**唯一漏斗**，到期/驱散/手动
    三条死亡路径全汇入，hook 只放一处；
  - **叠层 early return 不重发**（LIMITED/REFRESH 分支直接 return，表现已活着，
    与 UE 同款行为）；
- 测试：`GameplayCue.Status.Stun` 进 config、`ge_skeleton_stun.tres` 配
  `gameplay_cue_tags`、回归 count handler + register/unregister 生命周期；
  验证 OnActive ×1 / 驱散 OnRemoved ×1 / 到期 OnRemoved ×2，105 项全绿。

### 踩的坑（新账）

1. **迭代 Resource 本体崩溃**：`for tag in gameplay_cue_tags` → `_iter_next` 错误。
   容器是 Resource 不可迭代，正确姿势 `for tag in container._tags`（内部
   Dictionary，键是 FGameplayTag 对象——容器键**不是** StringName，StringName
   只在 `_saved_tag_names` 序列化通道；证据：container 内部 `_tags[tag]=true`、
   `matches_tag` 遍历调用都是对象）。
2. 报错定位训练：`(111, 38)` 类型错误引导"容器 vs 单 tag"概念辨析。

## 第 2 步：参数小票（关账）

### 设计讨论（用户驱动，好问题）

- 用户提议"直接传整个 spec 不就行了"——**三个反驳**：
  ① 解耦是双向的（表现不该摸到逻辑内脏：spec 装着 effect_def/modifiers/公式）；
  ② 生命周期：spec 是 RefCounted，持续表现活 2 秒，spec 可能先死（快照离手
  即定）；③ 参数最小集（飘字要数字、火花要位置、震屏要强度）；
- UE 正解：`FGameplayCueParameters` 轻量结构体，绝不传 spec 引用；
- 用户写 `_init(spec)` 构造器——被拦：变相传 spec + `spec.source_asc` 可为
  null（项目自带守卫先例 :329/:95-97）→ 正解：**小票空壳 + 广播点现场组装**，
  构造器不接 spec。

### 落地

- `GASGameplayCueParameters`（RefCounted 空壳：target/instigator/magnitude）；
- 签名三参统一全链路：`handler.call(tag, event, params)`（tag 必须带——数据当
  参数传，不存进薄类，注册表键是 tag 唯一的家）；
- `HandlerList.broadcast` 初版漏传 params（签名 3 参、调用 2 参）——审查抓出；
- magnitude 取 `spec.modifiers[0].get_magnitude()`，空则 0（execution 类 GE
  无 modifier 的缺口已记录，等真需求）；
- 测试：基础-24c（params.target 非空）、24d（纯标签 GE magnitude==0），
  107 项全绿。

## 第 3 步：凭票制 + 节点生灭（开局，未关账）

### 概念课（UE 的两套 API：消息 vs 挂载）

- `ExecuteGameplayCue`（fire-and-forget 消息）vs `AddGameplayCue` /
  `RemoveGameplayCue`（挂载，返回**句柄**）；
- 为什么持续 cue 必须被 spawn：① 生命周期需要载体（每帧推进）；② 状态需要
  存放处；③ 销毁需要句柄——Manager 追踪实例；
- **GE 生命周期 = cue 生命周期**：ASC 应用持续 GE 自动 Add、到期自动 Remove，
  中间的"等号"由 Manager 兑现；
- 重复 Add 同 tag：查 world 复用不重复 spawn（呼应"叠层不重发"）；
- **句柄制**：Add 返回票，Remove 凭票精确退场；ASC 的活跃效果条目（AGE）存
  着自己挂出去的票列表，到期逐张退场；Manager 内部仍按 tag 引用计数决定节点
  销毁。票 = 精确身份，计数 = 模糊身份，UE 选精确。

### 用户的两个好问题（设计修正的关键）

1. "两个人都眩晕 → 一颗星还是两颗星？"——**两颗**。实例身份是 `(tag, target)`
   不是 tag；UE 按 tag 全局复用一个 cue actor 是已知粗糙点，我们对齐语义但
   修正实例粒度；
2. "复数 tag / 复数 GE 共享 tag，移除时怎么知道删哪个？"——计数答得了"还有
   没人撑"，答不了"这局 GE 走了它的星必须灭"→ **凭票制**（门票代替引用原则
   第三次出场：effect handle 之后又一例）。

### 已落地部分（审查过，待改）

- `ActiveCue` 内嵌薄类（tag/target/node/count）；
- `_cue_instances: Dictionary[int, ActiveCue]`（票根 → 账页）+ `_active_cues`
  （组合键 `[tag, target]` → 账页，Array 可哈希按内容，对象按身份）+ 
  `_cue_factories: Dictionary[FGameplayTag, Callable]` + `_next_handle`;
- `register_factory` / `add_cue` 已写：查账 → 0→1 调工厂（`factory(params) ->
  Node`）挂 `target` 下 → 计数+1 → 先领号后自增 → 票根记账 → 返回票；
  没工厂也发票（表现空白合法，ASC 统一凭票退场）；
- 审查待修三处：① `var factory: Callable = ... else null` 非法（null 不能赋
  值类型变量）→ `_cue_factories.get(tag, Callable())`；② `node` 上类型
  `var node: Node = factory.call(params)`；③ register_factory 重复注册应 warn。
